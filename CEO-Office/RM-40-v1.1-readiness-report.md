## 3. What is **not** proven

This is the section that matters most, and none of it is a reason to stop — it
is the difference between "the system works" and "the system is running your
life".

1. **No live provider has been exercised in the default path.** Every adapter
   is proven against the contract harness, which is a controlled double. Real
   Telegram, Notion, Google, Canvas, Microsoft 365, DuitSini and Vercel calls
   sit behind an opt-in flag. The contract harness proves the *shape* of each
   interaction, not that your accounts behave that way today.
2. **The Azure Hermes service has not been activated yet.** The Phase 4
   implementation now includes a real Hermes API-server client and coordinator.
   It creates/reuses a durable session, sends a bounded envelope, validates the
   structured intent/role/Work Item plan, serves only Projection Broker briefs,
   gates tools, scans the final answer and records a payload-free turn. The
   controlled production-composition tracer proves this path without contacting
   a provider.

   Hermes Agent 0.21.0 successfully invoked GPT-5.6 Sol through the CEO's
   existing Codex OAuth session on 3 September 2026. For production, Hermes
   must be installed and authenticated as the Azure `real-ming` service
   account. Real-Ming receives only the private Hermes `API_SERVER_KEY` through
   Key Vault or the protected release environment; it never copies or manages
   the Codex OAuth token. The live activation and one-owner Telegram cutover
   are documented in `CEO-Office/RM-40-phase4-activation-runbook.md`.
3. **The dashboard has not been opened by you.** It is proven in a real browser
   against controlled state and now renders Hermes status/model/session/turn
   metadata without prompts or chain-of-thought. It is served from the Azure
   control plane and remains private; no public domain, TLS or identity-aware
   proxy has been approved.
4. **The 30-day backup rule is enforced by the backup adapter, not by the
   control plane**, which cannot see inside the backup store. The control plane
   purges what the adapter reports and records evidence only when the adapter
   proves the deletion — it cannot independently confirm nothing lingers.
5. **The append-only database triggers are unproven.** Six `RAISE(ABORT)`
   triggers guard the retention tables. Exercising them needs direct database
   access, which neither approved test seam provides, so they are correct by
   inspection only.
6. **The field-name Sensitive Secret hardening is not reachable through the
   approved test seams.** The guard exists, but RM-40 cannot claim behavioural
   proof until a public system or provider boundary can exercise it.
7. **Obsidian has no production destination yet.** The atomic materializer is
   wired to run after a successful Knowledge Compiler generation changes and
   defaults to the CEO Approved-Projection root. A host-local directory and
   any Lenovo sync policy still require the CEO's decision.
8. **`ceo-confirmed` career claims are unverified.** A claim labelled "CEO
   confirmed" is accepted at face value; there is no Approval record behind the
   label.

### Found by this ticket

RM-40 exists to catch what individual tickets miss, and it caught three things.

- **The Knowledge Health section of the dashboard rendered empty through the
  test seam.** Production wires it correctly, but the test harness did not, so
  no browser check could ever have proven that view — including the retention
  columns added days earlier. Fixed, and now pinned by a browser test that fails
  if the wiring, or either column, is removed.
- **RM-38's new dashboard columns had no test at all.** Now covered.
- **Financial Snapshots disappeared on process restart.** The ledger used an
  in-memory map despite the indefinite-retention rule. RM-40 added durable
  SQLite storage in the canonical control-plane database, preserves artifact
  bytes while allowing lifecycle fields to advance, rejects deletion, and
  proves restart/reopen retrieval through the Real-Ming System Harness.

## 4. Rollback and recovery readiness

| Property | State |
| --- | --- |
| Restart safety | Proven. The vault's append-only purge log is reconciled on every sweep, so a committed deletion is not left without central evidence if the process dies between the two writes. Verified by reopening a second control plane on the same state. |
| Idempotency | Proven. Repeated retention sweeps, repeated job runs and replayed commands produce one record, not two. |
| Deployment rollback | Proven. Promotion is bound to an exact candidate version; the predecessor stays readable. |
| Financial history | Proven. Snapshots supersede rather than overwrite; the predecessor workbook survives byte-for-byte, and the ledger survives control-plane restart in canonical SQLite storage. |
| **Off-host backup** | **Not in place.** Local backup meets every acceptance criterion, but losing the Azure VM loses the operations state. This is the single largest recovery gap. |
