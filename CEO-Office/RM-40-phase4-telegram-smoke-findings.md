# RM-40 Phase 4 Telegram smoke findings

## TL;DR

The 5 September 2026 CEO smoke test proves that ordinary Telegram messages
reach the real Hermes agent on Malaysia West. It does **not** pass the expected
Telegram experience or prove the complete coding workflow. Development work
remains; no further OAuth or Tailscale sign-in is needed.

All six Real-Ming answer records matched the corresponding JSON `answer`
values in Hermes's native session database. The native session reported
`api_server`, `gpt-5.6-sol`, ten model API calls and one `skill_view` tool call
at inspection. These counters describe different layers and are not expected
to equal six delivered Telegram turns. Only metadata and match counts were
read back; no OAuth values or hidden reasoning were retrieved.

## Confirmed findings

| Finding | Evidence | Effect |
| --- | --- | --- |
| Real Hermes is connected | Six of six persisted Real-Ming answers match native Hermes answers; deployed image matches the approved digest | The observed ordinary replies are generated by Hermes, not the old fixed answer worker |
| Native Telegram presentation is bypassed | Real-Ming owns `sendMessage`; the installed Hermes Telegram adapter is not this bot's transport | Native typing, formatting and streaming behavior are not inherited automatically |
| No typing indicator | Real-Ming transport has no `sendChatAction` operation | The chat shows no processing feedback while a reply is being generated |
| No rich formatting | Provider harness sends Markdown without `parse_mode` or `entities` | Formatting markup cannot render; newlines are preserved |
| Restrictive answer instruction | `hermes-runtime-client.ts` requires one JSON object with “no Markdown, no preamble” | The instruction is ambiguous about Markdown inside `answer`; the observed final answers contain no line breaks |
| Complete-response delivery | Real-Ming calls `/api/sessions/{id}/chat`, not the installed `/chat/stream` endpoint | Telegram waits for the complete result; no partial answer or native tool progress is relayed |
| Role-prefixed commands bypass Hermes | `CTO: ...` enters the legacy action parser; reproduced through the System Harness with no additional Hermes call | Not all messages follow the approved Hermes-first decision path |
| Proposed coding tools are not wired | Production constructs the Hermes coordinator without `executeTool`; its controlled test explicitly expects `workspace.read` denial | Capturing a Work Item is not proof that Hermes can complete the governed coding loop |
| Knowledge activation is missing | Production CLI does not pass `knowledgeOperations`; the export directory and dashboard knowledge list are empty | Obsidian will not become populated merely by waiting for the scheduler |

The screenshot's bot explanation is only partly correct. Real-Ming already
extracts the `answer` field; it does not send the entire control JSON as the
user-facing message. The renderer lacks formatting, and the model supplied
single paragraphs. JSON itself can carry line breaks, lists and code blocks
inside a string, so JSON alone does not require poor readability.

Native Hermes tools are not globally disabled: a real `skill_view` call was
observed. That is separate from the unbound Real-Ming `toolRequests` path and
does not prove workspace read/write/test execution or policy enforcement over
native tools. Those boundaries need integration tests before coding readiness
can be claimed.

## Verification performed

1. Read-only production checks confirmed Hermes and Real-Ming active on the
   Malaysia host and the exact approved image digest.
2. A read-only join compared persisted answer strings across the Real-Ming
   mapping and native Hermes database: six matches from six turns.
3. A provider-contract diagnostic sent formatted sample text to the controlled
   Telegram edge. Delivery succeeded, newlines remained, and the assertion
   requiring formatting metadata failed. No live Telegram request was made.
4. A System Harness diagnostic compared an ordinary request with the same
   request prefixed `CTO:`. The first called Hermes; the second created a Work
   Item through the old path. The assertion requiring another Hermes call
   failed. No live Notion record was created.
5. Native session timestamps showed user-to-assistant intervals of roughly
   3.8–14.5 seconds for the observed pairs. These are not measurements of the
   complete phone-to-phone latency and do not establish every latency cause.

The diagnostic failures are evidence of unresolved defects, not passing
acceptance tests. No runtime source, installed Hermes code, transport ownership
or production image was changed during this diagnosis.

## Required next work

**V6 update:** the diagnosis above stands, but the latest recommendation is to reuse the native Hermes Telegram gateway and extension APIs rather than rebuild its presentation in the wrapper. The following list records the original repair scope; use the [V6 architecture review](RM-40-v6-architecture-review.md) and [new diagram](../docs/architecture/real-ming-agent-diagram-v6.html) for the revised implementation direction.

1. Add typing feedback, Telegram-safe formatted delivery and appropriate long
   reply handling; allow normal formatting inside the user-facing answer.
2. Ensure role-addressed conversational requests still reach Hermes; preserve
   exact approval callbacks as control operations.
3. Integrate Hermes's native execution and events with the Real-Ming context,
   policy and evidence interfaces. Prove a real bounded workspace read, edit
   and test loop; do not call a denied proposal successful execution.
4. Activate Knowledge Operations and a permitted source/projection path, then
   verify the CEO-only Obsidian export.
5. Rerun Telegram, dashboard, durable replay and recovery acceptance checks.
   Keep the East Asia rollback VM retained while activation remains incomplete.

The architecture does not require a different LLM. The implementation must
preserve the Hermes experience while supplying the Real-Ming integrations.
